[STUDENT]: In this code, req.body acts as a container object holding all the data submitted by the user. The values cycle from the user's browser to your backend controller through a 3-step pipeline: 

1. The HTML Form Attributes (Frontend): When a user types into a form and clicks submit, the browser packages the input values based on the HTML name attributes. 
2. The HTTP Request Transmission: When submitted, the browser sends an HTTP POST request to the server. It encodes the form fields into the body of the network request as a string. 
3. Express Middleware Parsing (Backend): By default, Node.js/Express treats the incoming request body as raw stream data. To convert that string back into a usable JavaScript object, your app relies on body-parsing middleware configured in your core server file (server.js or index.js). This middleware intercepts the request, reads the string, parses it, and dynamically attaches the resulting object to the req object as req.body before passing it to the processNewProjectForm function.

[COACH]: Thank you for sharing that screenshot of your flash.js middleware file! This is a fantastic, custom implementation of flash functionality built right on top of the Express session object.

Looking at lines 24 to 31, your middleware checks if req.session.flash exists, and if not, it initializes an object with empty arrays for success, error, warning, and info.

In your own words, why is it necessary to store these flash messages specifically inside the session object (req.session), rather than just using a standard global variable or a regular property on the req object? Why does flash messaging rely so heavily on the session?

[STUDENT]: The Express req (request) object lives and dies within a single HTTP request-response cycle.

The Problem: When your controller finishes processing a form submission, it typically issues a redirect command: res.redirect('/projects').

The Result: A redirect forces the user's browser to discard the current request page and make a completely brand-new HTTP request to the new URL. If you attach data to req.flash, that entire req object is instantly destroyed during the redirect, losing the message before the new page can display it. 

If you store messages in a global backend variable (e.g., global.flashMessage = "Success!"), that memory space is shared by every single person visiting your website simultaneously.

[COACH]: That is an absolutely flawless explanation! You perfectly articulated the stateless nature of the req object and correctly highlighted the data-leak risks of using a global variable where users could see each other's messages. Using the session to persist data across that redirect cycle is exactly why flash messages work. Excellent job!
